### 2.1 Выводы по обзору

1. **Ревью кода в основном про сопровождаемость и соглашения.** Большая часть замечаний ревьюеров касается улучшения кода и понимания изменения, а не только ошибок [1]. Единый стиль и читаемость – одна из главных целей ревью в Google [2]. Соглашения – массовый предмет замечаний [18], а правила кодирования и экспертиза исходного кода закреплены как процессы разработки безопасного ПО [22].
2. **У каждого замечания есть цена.** Время на сопровождение изменения растет почти линейно с числом замечаний [13], а большое число замечаний на файл связано с их меньшей полезностью [4]. Поэтому ложное замечание не нейтрально: оно отнимает время автора и ревьюера.
3. **Ложные срабатывания убивают доверие к инструменту.** Это известно по статическому анализу [7, 17]. В Google анализатор допускают в ревью только при малой доле «эффективных ложных срабатываний», то есть предупреждений, на которые разработчик не реагирует [12].
4. **LLM-ревью пока шумное.** У агентного ревью CodeRabbit отклоняется 56,3 % замечаний, среди причин – ложные срабатывания и расхождение с практиками команды [5]. В промышленном внедрении PR-Agent время закрытия PR выросло с 5 ч 52 мин до 8 ч 20 мин, разработчики жаловались на ошибочные замечания [23]. Бенчмарки описывают компромисс между полнотой и ложными находками [24, 25]. Об этом же говорят опрос разработчиков [26] и обзоры применения LLM к анализу кода [21].
5. **Отсев ложных сообщений работает и измерим.** Классификатор на признаках анализатора отсеивает ложные предупреждения Svace с точностью выше 93 % [8], LLM поднимает точность SharpChecker до 10 п. п. [9]. Отдельная инструкция-фильтр в 2,5 раза повышает долю применимых рецензий к коду [10]. Отклонение замечаний CodeRabbit предсказуемо с F1 до 76 % [5].
6. **Мультиагентный подход и контроль агентов уже исследуются.** Есть обзор мультиагентных LLM-систем для программной инженерии [20], системы ревью с надзорным агентом [27] и агентом-критиком [28], промышленное мультиагентное ревью с точностью 96 % [16]. LLM в роли судьи согласуется с людьми не хуже, чем люди между собой, но имеет известные смещения [29]; критик может впасть в «ложный консенсус» с ревьюером [28].
7. **Подходы, которые стоит использовать:** агенты по темам замечаний [1, 16], отдельный проверяющий агент [10, 28] с доступом к коду и структурированному контексту [9], привязка замечания к конкретному правилу [14], оценка по совпадению с замечаниями людей [19, 25] с предварительной очисткой эталона [6, 11].
8. **Нерешенные вопросы:** нет методики, которая проверяет каждое LLM-замечание по коду и по тексту правила команды до публикации и при этом измеряет и долю ложных замечаний, и полноту относительно живых ревьюеров на реальных MR. Почти все данные англоязычные, а соглашения команд, записанные на русском языке, в открытых работах не рассматриваются.

## 3 Обзор и сравнение аналогов

### 3.1 Прямые аналоги

Прямые аналоги – сервисы, которые автоматически оставляют замечания LLM в PR или MR.

1. **CodeRabbit** ([coderabbit.ai](https://www.coderabbit.ai/)) – коммерческий сервис ревью PR и MR. Инструкции для путей и файлы правил кодирования задаются в репозитории, предпочтения команды накапливаются как «learnings», громкость ревью регулируется профилем, язык ответов можно выбрать, в том числе русский [30]. Ограничения: отдельного шага проверки замечаний в документации нет, шумом управляет только профиль; по независимому исследованию отклоняется 56,3 % его замечаний [5]. Развертывание у заказчика доступно только в корпоративном тарифе.
2. **Qodo** ([qodo.ai](https://www.qodo.ai/)) – коммерческая платформа ревью. Специализированные агенты параллельно оценивают изменение, затем агент-судья объединяет находки и отбрасывает находки с низкой уверенностью [31]. Ограничения: закрытая система, как судья проверяет находку и связывает ее с правилом, не раскрыто.
3. **PR-Agent** ([github.com/qodo-ai/pr-agent](https://github.com/qodo-ai/pr-agent)) – открытый проект, из которого вырос Qodo. Поддерживает GitLab и любые модели через LiteLLM, включая локальные [32]. Ограничения: каждый инструмент делает один вызов LLM [32]; фильтрация сводится к самооценке предложений той же моделью и порогу оценки [33]. Именно на его основе получено удлинение ревью в промышленном исследовании [23].
4. **GitHub Copilot code review** ([github.com/features/copilot](https://github.com/features/copilot)) – встроенный ревьюер GitHub: агент сам собирает контекст репозитория и читает файлы инструкций [34]. По данным вендора, в 71 % ревью есть полезное замечание, а в 29 % агент молчит, чтобы не шуметь [35]. Ограничения: нет GitLab, модель выбрать нельзя [34], качество меряется реакциями пользователей.
5. **Greptile** ([greptile.com](https://www.greptile.com/)) – ревьюер, который строит граф репозитория. Правила команды задаются файлами с областью действия и серьезностью, есть параметр строгости [36]. Можно развернуть в изолированной сети с GitLab Self-Managed и своей моделью через OpenAI-совместимый API [37]. Ограничения: закрытый продукт, отдельного проверяющего агента в документации нет.
6. **Claude Code Review** ([code.claude.com](https://code.claude.com/docs/en/code-review)) – сервис Anthropic: несколько агентов ищут проблемы, отдельный шаг сверяет кандидатов с кодом и отсеивает ложные срабатывания, затем находки ранжируются [38]. По схеме это ближайший аналог ВКР. Ограничения: только GitHub, работает только на инфраструктуре Anthropic, свою модель подключить нельзя [38].
7. **GitLab Duo Code Review Flow** ([docs.gitlab.com](https://docs.gitlab.com/user/duo_agent_platform/flows/foundational_flows/code_review/)) – агентное ревью GitLab из двух этапов: сбор контекста и ревью. Инструкции команды хранятся в `.gitlab/duo/mr-review-instructions.yaml`, поддерживаются Self-Managed и собственные модели [39]. Ограничения: шага проверки замечаний нет, обратная связь на последующие ревью не влияет, что прямо сказано в документации [40].
8. **GigaCode-агент в GitVerse** ([gitverse.ru](https://gitverse.ru/)) – российский агент ревью запросов на слияние. Правила проекта берутся из Markdown-файлов каталога `.gitverse/pr_rules/`, команда `/improve` оценивает важность предложений [41]. Ограничения: работает только в GitVerse, отдельной проверки замечаний и ссылки на правило нет.

### 3.2 Косвенные аналоги

Косвенные аналоги решают часть задачи другим способом.

1. **Semgrep Assistant** ([semgrep.dev](https://semgrep.dev/)) – ИИ-проверка находок статического анализа перед публикацией в MR: если находка признана ложной, комментарий не публикуется. По данным вендора, отсеивается в среднем 60 % находок, люди согласны с решениями в 96 % случаев [42]. Ограничения: проверяет находки детерминированных правил, а не замечания LLM по соглашениям на естественном языке.
2. **SonarQube** ([sonarsource.com](https://www.sonarsource.com/)) – статический анализ с правилами, у которых есть идентификаторы, и условиями на новый код, статус которых показывается в MR GitLab [43]. Ограничения: правила пишутся кодом и проверяют формализуемые свойства, смысловые соглашения команды так не выразить.
3. **Google AutoCommenter** [14] – внутренняя система Google: LLM проверяет лучшие практики, замечание ссылается на документ практики. Ограничения: недоступна снаружи, шум снижается порогами уверенности и отключением шумных правил, а не проверкой каждого замечания.
4. **CodeAgent** [27] – исследовательская мультиагентная система ревью с надзорным агентом. Ограничения: надзорный агент следит, чтобы ответы не уходили от вопроса, а не проверяет правоту замечания по коду; оценка на открытых датасетах, без соглашений конкретной команды.
5. **Линтеры с собственными правилами** (например, ESLint, [eslint.org](https://eslint.org/)) – детерминированные проверки синтаксиса с почти нулевой долей ложных срабатываний. Ограничения: проверяют только то, что формализуется на уровне синтаксического дерева. Задают границу: формализуемые правила разумно отдать линтеру, а LLM оставить смысловые соглашения.

### 3.3 Таблица сравнения

**Почему выбраны эти критерии.** Критерии 1 и 2 следуют из предмета работы: соглашения команды записаны текстом и замечание должно указывать нарушенное правило, как в AutoCommenter [14]. Критерии 3 и 4 отражают главную проблему – ложные замечания [5, 23] – и способ ее решения: специализированные агенты и отдельная проверка [10, 16]. Критерий 5 – учет истории ревью. Критерии 6 и 7 – условия целевой среды: self-hosted GitLab и код под NDA, который нельзя отправлять внешнему провайдеру. ### 3.4 Выводы по сравнению

1. Ни один аналог не сочетает ссылку замечания на номер правила команды, проверку каждого замечания перед публикацией и работу в закрытом контуре с self-hosted GitLab и своей моделью. Те, у кого есть проверка (Claude Code Review, Qodo), закрыты и не работают в нужной среде; те, кто работает в нужной среде (GitLab Duo, Greptile, PR-Agent), не проверяют замечания отдельным агентом.
2. Из Claude Code Review и Qodo берем схему «агенты-искатели по темам, затем проверяющий агент» [31, 38]. Из Semgrep Assistant – правило «ложную находку не публиковать» и метрику согласия людей с решениями фильтра [42].
3. Из AutoCommenter берем привязку замечания к правилу [14], но правила – это пронумерованные соглашения самой команды на русском языке, а не общие лучшие практики.
4. Из PR-Agent и GitLab Duo берем способ доставки замечаний в MR self-hosted GitLab и работу со своей моделью [32, 39].
5. Качество аналогов меряется несопоставимо: реакции пользователей, свои бенчмарки, оценка своими инженерами. Сравнения с замечаниями живых ревьюеров на реальных MR команды ни у одного аналога нет, поэтому методика такой оценки – самостоятельный результат работы.

## 4 Итоги

**Итоговая тема ВКР:** Снижение доли ложных замечаний при автоматизированном ревью кода мультиагентной системой на основе больших языковых моделей с учетом соглашений команды разработки

**УДК для тезиса:** 004.415.5:004.89

**Ключевые слова:** ревью кода; запрос на слияние; большие языковые модели; мультиагентные системы; ложные срабатывания; соглашения о коде; правила кодирования; LLM в роли судьи; качество программного обеспечения.

**Объект исследования:** процесс ревью изменений программного кода в команде разработки.

**Предмет исследования:** методы автоматизированного ревью кода мультиагентной системой на основе LLM с проверкой замечаний на соответствие коду и соглашениям команды.

### 4.1 Актуальность исследования

Ревью кода – обязательный этап разработки в большинстве команд, а значительная часть замечаний на нем касается не ошибок, а сопровождаемости и соблюдения принятых в команде соглашений [1, 2, 18]. Правила кодирования и экспертиза исходного кода входят в процессы разработки безопасного ПО по ГОСТ Р 56939-2024 [22]. Каждое замечание стоит автору времени: время сопровождения изменения растет почти линейно с числом замечаний [13].

ИИ-ассистенты для кода используются массово: в России их используют или тестируют 75 % опрошенных ИТ-специалистов, а соответствие кода нормам и стандартам называют метрикой эффективности команды 29 % [44]. LLM-ревью уже встроено в GitHub, GitLab и российские платформы [34, 39, 41]. Но такие ревьюеры шумят: у агентного ревью CodeRabbit отклоняется 56,3 % замечаний, в том числе из-за ложных срабатываний и расхождения с практиками команды [5], а в промышленном внедрении PR-Agent время закрытия PR выросло с 5 ч 52 мин до 8 ч 20 мин [23]. Главная фрустрация разработчиков от ИИ – ответы «почти правильные, но не совсем» (66 %), а не доверяют точности ИИ 45,7 % [26]. По опыту статического анализа известно, что инструмент с большой долей ложных срабатываний перестают использовать [12, 17].

Отсев ложных сообщений до человека показал эффект в статическом анализе [8, 9, 42] и в генерации рецензий [10], а отклонение LLM-замечаний предсказуемо [5]. Мультиагентное ревью с проверяющим агентом – направление 2024–2026 годов [16, 27, 28, 38]. Но проверка каждого замечания по коду и по тексту правила самой команды, работа в закрытом контуре с self-hosted GitLab и оценка относительно живых ревьюеров вместе не реализованы ни в одном аналоге (раздел 3).

Автор применяет прототип такого конвейера на ревью MR в коммерческом проекте: агенты по темам замечаний, проверяющий агент и пронумерованные соглашения команды. Количественной оценки этого опыта пока нет, ее получение – задача 5. Поэтому разработка и измеримая оценка такой системы своевременны и востребованы практикой.

### 4.2 Цель исследования

Снизить долю ложных замечаний автоматизированного ревью MR без существенной потери полноты за счет мультиагентной системы на основе LLM, в которой агенты по темам находят нарушения пронумерованных соглашений команды, а проверяющий агент сверяет каждое замечание с кодом и текстом правила до публикации. Система работает в контуре компании с self-hosted GitLab и своей моделью.

Целевые показатели:
- доля ложных замечаний снижается не менее чем в 2 раза по сравнению с той же системой без проверяющего агента. Обоснование: ИИ-фильтр находок статического анализа отсеивает в среднем 60 % находок при 96 % согласия людей [42], отдельный этап фильтрации поднимает долю применимых рецензий в 2,5 раза [10]. Значение «в 2 раза» – рабочая гипотеза, уточняется замером на эталоне (задача 5);
- полнота относительно замечаний живых ревьюеров снижается не более чем на 10 % от полноты системы без проверяющего агента; порог – рабочая гипотеза, уточняется замером;
- не менее 90 % замечаний по соглашениям указывают правило, которое действительно нарушено в этом месте кода, по ручной проверке выборки;
- код и замечания не покидают контур компании: все вызовы модели идут к модели, развернутой в контуре.

### 4.3 Задачи исследования

1. Формализовать представление соглашений команды (номер, текст, область действия, примеры) и классификацию замечаний ревью (требования задачи, архитектура, код и соглашения, тесты, комментарии).
2. Собрать эталон: замечания живых ревьюеров на реальных MR с разметкой категорий, очистить его от расплывчатых и неприменимых замечаний [6, 11].
3. Разработать архитектуру мультиагентной системы: агенты-искатели по темам замечаний и проверяющий агент, который получает доступ к коду репозитория и требует доказательство с указанием файла и строки; учесть смещения LLM в роли судьи [28, 29].
4. Реализовать прототип для self-hosted GitLab со своей моделью: получение изменений MR, запуск агентов, публикация прошедших проверку замечаний.
5. Разработать методику оценки по точности, полноте и доле ложных замечаний относительно живых ревьюеров; сравнить систему с вариантом без проверяющего агента, с самооценкой одной модели (как в PR-Agent [33]) и с одноагентным ревью.
