### 2.1 Выводы по обзору

1. **Ревью кода в основном про сопровождаемость и соглашения.** Большая часть замечаний ревьюеров касается улучшения кода и понимания изменения, а не только ошибок [1]. Единый стиль и читаемость – одна из главных целей ревью в Google [2]. Правила кодирования и экспертиза исходного кода закреплены как процессы разработки безопасного ПО [23]. Соглашения можно выводить из кода автоматически [19], но так не получить правила, которые команда сформулировала сама.
2. **У каждого замечания есть цена.** Время на сопровождение изменения растет почти линейно с числом замечаний [13], а большое число замечаний на файл связано с их меньшей полезностью [4]. Поэтому ложное замечание не нейтрально: оно отнимает время автора и ревьюера.
3. **Ложные срабатывания подрывают доверие к инструменту.** Это известно по статическому анализу [7, 17]. В Google анализатор допускают в ревью только при малой доле «эффективных ложных срабатываний», то есть предупреждений, на которые разработчик не реагирует [12].
4. **LLM-ревью пока шумное.** У агентного ревью CodeRabbit отклоняется 56,3 % замечаний; среди причин – ложные срабатывания, избыточность, выход за рамки задачи и расхождение с практиками кодирования [5]. Промышленное внедрение PR-Agent сопровождалось ростом времени закрытия PR (pull request) с 5 ч 52 мин до 8 ч 20 мин и жалобами на ошибочные замечания [18]. Бенчмарки описывают компромисс между полнотой и ложными находками [24, 25]. Главная фрустрация разработчиков от ИИ – решения «почти правильные, но не совсем» [26], а надежность выводов LLM при анализе кода остается открытой проблемой [22].
5. **Отсев ложных сообщений работает и измерим.** Классификатор на признаках анализатора отсеивает ложные предупреждения Svace с точностью выше 93 % [8], LLM повышает точность SharpChecker на величину до 10 п. п. при сохранении 80–97 % истинных предупреждений [9]. Доработка инструкций вместе с LLM-фильтром в 2,5 раза повышает долю применимых рецензий к коду, причем одна фильтрация такого прироста не дает [10]. Отклонение замечаний CodeRabbit предсказуемо с F1 до 76 % [5].
6. **Мультиагентный подход и контроль агентов уже исследуются.** Есть обзор мультиагентных LLM-систем для программной инженерии [21], системы ревью с надзорным агентом [27] и агентом-критиком [28], промышленное мультиагентное ревью, где 96 % находок признаны верными [16]. LLM в роли судьи согласуется с людьми не хуже, чем люди между собой, но имеет известные смещения [29]; критик может впасть в «ложный консенсус» с ревьюером [28].
7. **Подходы, которые стоит использовать:** агенты по темам замечаний [1, 16], отдельный проверяющий агент [10, 28] с доступом к коду и структурированному контексту [9], привязка замечания к конкретному правилу [14], оценка по совпадению с замечаниями людей [20, 25] с предварительной очисткой эталона [6, 11].
8. **Нерешенные вопросы.** В рассмотренных работах замечания либо фильтруются одной моделью без проверки по коду [10], либо проверяются по коду, но для детерминированных правил анализатора [8, 9]. Проверка LLM-замечаний по коду и по тексту пронумерованных соглашений самой команды с измерением и доли ложных замечаний, и полноты относительно живых ревьюеров в найденных работах не описана. Русскоязычные работы по ревью [10, 11, 20] используют рецензии к коду, но не соглашения конкретной команды.

## 3 Обзор и сравнение аналогов

### 3.1 Прямые аналоги

Прямые аналоги – сервисы, которые автоматически оставляют замечания LLM в PR или MR (merge request).

1. **CodeRabbit** ([coderabbit.ai](https://www.coderabbit.ai/)) – коммерческий облачный сервис ревью. Инструкции для путей и файлы правил кодирования задаются в репозитории, предпочтения команды накапливаются как «learnings», громкость ревью регулируется профилем, язык ответов можно выбрать, в том числе русский [30]. Подключается к self-managed GitLab [31]. Ограничения: отдельного шага проверки замечаний в документации нет, шумом управляет только профиль; по независимому исследованию отклоняется 56,3 % его замечаний [5].
2. **Qodo** ([qodo.ai](https://www.qodo.ai/)) – коммерческая платформа ревью. Специализированные агенты параллельно оценивают изменение, затем агент-судья объединяет находки и отбрасывает находки с низкой уверенностью [32]. Учитывает историю PR: замечания, похожие на ранее исправленные, повышаются в приоритете, на ранее отклоненные – понижаются [33]. Разворачивается у заказчика, в том числе с GitLab Server [34]. Ограничения: закрытая система; как судья проверяет находку и связывает ли ее с правилом команды, не раскрыто; работа со своей моделью в документации не описана.
3. **PR-Agent** ([github.com/The-PR-Agent/pr-agent](https://github.com/The-PR-Agent/pr-agent)) – бывший открытый проект Qodo, теперь его поддерживает сообщество. Поддерживает GitLab и любые модели через LiteLLM, включая локальные [35]. Ограничения: фильтрация сводится к самооценке предложений моделью по шкале с порогом, который по умолчанию выключен [36]; проверки замечания по коду нет. На его основе выполнено промышленное исследование [18].
4. **GitHub Copilot code review** ([github.com/features/copilot](https://github.com/features/copilot)) – встроенный ревьюер GitHub: один агент сам собирает контекст репозитория и читает файлы инструкций, есть память о репозитории в режиме предварительного доступа [37]. По данным вендора, в 71 % ревью есть полезное замечание, а в 29 % агент молчит, чтобы не шуметь [38]. Ограничения: нет GitLab, модель выбрать нельзя [37].
5. **Greptile** ([greptile.com](https://www.greptile.com/)) – ревьюер, который строит граф репозитория. Правила команды задаются файлами с областью действия и серьезностью, по каждому правилу считается число оставленных по нему замечаний и доля исправленных [39]. Учитывает реакции на свои замечания [40]. Разворачивается в изолированной сети с GitLab Self-Managed и своей моделью через OpenAI-совместимый API [41]. Ограничения: закрытый продукт, отдельного проверяющего агента в документации нет, ложное замечание учитывается только после публикации.
6. **Claude Code Review** ([code.claude.com](https://code.claude.com/docs/en/code-review)) – сервис Anthropic: несколько агентов параллельно ищут проблемы, отдельный шаг сверяет кандидатов с кодом и отсеивает ложные срабатывания, затем находки ранжируются [42]. Правила ревью задаются файлами репозитория, их получают и ищущие, и проверяющие агенты [43]. По схеме это ближайший аналог ВКР. Ограничения: только GitHub, работает только на инфраструктуре Anthropic, свою модель подключить нельзя [42].
7. **GitLab Duo Code Review Flow** ([docs.gitlab.com](https://docs.gitlab.com/user/duo_agent_platform/flows/foundational_flows/code_review/)) – агентное ревью GitLab из двух этапов: сбор контекста и ревью; поддерживаются Self-Managed и собственные модели, повторное ревью того же MR учитывает ответы на прежние замечания [44]. Инструкции команды хранятся в `.gitlab/duo/mr-review-instructions.yaml` [45]. Ограничения: шага проверки замечаний нет, обратная связь не влияет на ревью других MR [46].
8. **GigaCode-агент в GitVerse** ([gitverse.ru](https://gitverse.ru/)) – российский агент ревью запросов на слияние. Правила проекта берутся из Markdown-файлов каталога `.gitverse/pr_rules/`, команда `/improve` оценивает важность предложений [47]. Ограничения: работает только в GitVerse, отдельной проверки замечаний и ссылки на правило в документации нет.

### 3.2 Косвенные аналоги

Косвенные аналоги решают часть задачи другим способом.

1. **Semgrep Multimodal** (ранее Semgrep Assistant, [semgrep.dev](https://semgrep.dev/)) – ИИ-проверка находок статического анализа: каждая находка проверяется с дополнительным контекстом, и если она признана ложной, комментарий в запрос на слияние не публикуется [48]. По данным вендора, отсеивается в среднем 60 % находок, люди согласны с решениями в 96 % случаев [49]. Ограничения: проверяет находки детерминированных правил, а не замечания LLM по соглашениям на естественном языке.
2. **Google AutoCommenter** [14] – внутренняя система Google: модель проверяет лучшие практики, замечание ссылается на документ практики. Ограничения: недоступна снаружи; шум снижали порогами уверенности и отключением целых практик, а не проверкой каждого замечания.
3. **CodeAgent** [27] – исследовательская мультиагентная система ревью с надзорным агентом. Ограничения: надзорный агент следит, чтобы ответы агентов не уходили от вопроса ревью, а не проверяет правоту замечания по коду; оценка на открытых датасетах, без соглашений конкретной команды.
4. **SonarQube** ([sonarsource.com](https://www.sonarsource.com/)) и линтеры с собственными правилами (например, ESLint, [eslint.org](https://eslint.org/)) – детерминированные правила с идентификаторами и условия на новый код, статус которых показывается в запросе на слияние [50]. Ограничения: проверяют только формализуемые свойства кода. Задают границу работы: формализуемые правила разумно отдать анализатору, а LLM оставить смысловые соглашения. В таблицу сравнения не включены, так как не формируют замечания на естественном языке.

### 3.3 Таблица сравнения

Критерии сравнения:

1. Соглашения команды хранятся текстом в репозитории.
2. Замечание ссылается на конкретное правило.
3. Каждое замечание отдельно проверяется перед публикацией.
4. Замечания ищут специализированные агенты по темам.
5. Учитываются обратная связь и история ревью.
6. Поддерживается self-hosted GitLab.
7. Работает со своей моделью в контуре компании.
8. Опубликована метрика качества с методикой относительно действий людей.
9. Замечания пишутся на русском языке.

**Почему выбраны эти критерии.** Критерии 1 и 2 следуют из предмета работы: соглашения записывает сама команда, а замечание должно указывать нарушенное правило, как в AutoCommenter [14]. Критерии 3 и 4 отражают главную проблему – ложные замечания [5, 18] – и способ ее решения: специализированные агенты и отдельная проверка [16, 42]. Критерий 5 нужен, потому что часть отклонений связана с практиками конкретной команды [5], а история ревью – источник этих практик и эталона. Критерии 6 и 7 – условия целевой среды: код коммерческого проекта под NDA (Non-Disclosure Agreement) хранится в self-hosted GitLab и не может отправляться внешнему провайдеру, а часть аналогов работает только в облаке вендора [37, 42]. Критерий 8 – можно ли проверить заявленное качество. Критерий 9 – замечания на языке команды.

Обозначения: «+» – есть, «±» – частично, «–» – нет или не заявлено в использованной документации.

**Как получены оценки.** PR-Agent оценен по исходному коду и конфигурации [35, 36], AutoCommenter и CodeAgent – по статьям [14, 27]. Остальные аналоги – закрытые системы, поэтому их оценки **экспертные**: они сделаны автором по официальной документации, на которую даны ссылки в подразделах 3.1 и 3.2, и отмечены знаком «\*». «–\*» означает «в документации не заявлено», а не доказанное отсутствие функции.

### 3.4 Выводы по сравнению

1. По использованной документации ни один аналог не сочетает ссылку замечания на правило команды, проверку каждого замечания перед публикацией и работу со своей моделью в self-hosted GitLab. Проверка замечаний есть у Claude Code Review и Qodo, но первый работает только с GitHub в облаке вендора, а у второго не описана работа со своей моделью. GitLab Duo, Greptile и PR-Agent работают в нужной среде, но не проверяют каждое замечание отдельно.
2. Из Claude Code Review и Qodo берем схему «агенты-искатели, затем проверяющий агент» [32, 42] и требование доказательства с указанием файла и строки [43]. Из Semgrep Multimodal – правило «ложную находку не публиковать» и метрику согласия людей с решениями фильтра [48, 49].
3. Из AutoCommenter берем привязку замечания к правилу и ориентир доли полезных замечаний [14], но правила – это пронумерованные соглашения самой команды на русском языке, а не общие лучшие практики. Из Greptile – учет замечаний и исправлений по каждому правилу [39].
4. Из PR-Agent и GitLab Duo берем способ доставки замечаний в MR self-hosted GitLab и работу со своей моделью [35, 44]. PR-Agent используется как базовая линия.
5. Оценка по замечаниям людей уже применяется в исследованиях [20, 25], но не на закрытых MR команды с русскоязычными соглашениями и с проверкой того, что указанное правило действительно нарушено. Такая методика оценки – часть результата работы.

## 4 Итоги

**Итоговая тема ВКР:** Снижение доли ложных замечаний при автоматизированном ревью кода мультиагентной системой на основе больших языковых моделей с учетом соглашений команды разработки

**УДК для тезиса:** 004.415.5:004.89

**Ключевые слова:** ревью кода; запрос на слияние; большие языковые модели; мультиагентные системы; ложные срабатывания; соглашения о коде; правила кодирования; LLM в роли судьи; качество программного обеспечения.

**Объект исследования:** процесс ревью изменений программного кода в команде разработки.

**Предмет исследования:** методы автоматизированного ревью кода мультиагентной системой на основе LLM с проверкой замечаний на соответствие коду и соглашениям команды.

**Охват.** Система проверяет изменения на соответствие соглашениям команды – правилам об архитектуре, коде и именовании, тестах и комментариях. Замечания о том, выполнены ли требования задачи, в охват не входят: для них нужен текст задачи и знание предметной области.

**Ложное замечание** – замечание, которое разметчики признали неверным по существу: описанной проблемы в коде нет, или указанное правило к этому месту не применимо. Верное, но отклоненное разработчиком замечание (избыточное, вне рамок задачи) ложным не считается и учитывается отдельно, так как в исследованиях эти причины отклонения различаются [3, 5].

### 4.1 Актуальность исследования

Ревью кода – обязательный этап разработки в крупных компаниях, и значительная часть замечаний на нем касается не ошибок, а сопровождаемости и соблюдения принятых соглашений [1, 2]. Правила кодирования и экспертиза исходного кода входят в процессы разработки безопасного ПО по ГОСТ Р 56939-2024 [23]. Каждое замечание стоит автору времени: время сопровождения изменения растет почти линейно с числом замечаний [13].

ИИ-ассистенты для кода используются массово: в России их используют или тестируют 75 % опрошенных ИТ-специалистов, а соответствие кода нормам и стандартам называют метрикой эффективности команды 29 % [51]. LLM-ревью уже встроено в GitHub и GitLab [37, 44] и в российскую платформу GitVerse [47]. Но такие ревьюеры шумят: у агентного ревью CodeRabbit отклоняется 56,3 % замечаний, в том числе из-за ложных срабатываний и расхождения с практиками команды [5], а промышленное внедрение PR-Agent сопровождалось ростом времени закрытия PR с 5 ч 52 мин до 8 ч 20 мин [18]. Даже в AutoCommenter доля полезных замечаний остановилась около 54 % при целевых 80 % [14]. Главная фрустрация разработчиков от ИИ – решения «почти правильные, но не совсем» (66 %), а не доверяют точности ИИ 45,7 % [26]. По опыту статического анализа известно, что инструмент с большой долей ложных срабатываний перестают использовать [12, 17].

Отсев ложных сообщений до человека показал эффект в статическом анализе [8, 9, 49]. В генерации рецензий одна фильтрация давала меньший прирост, чем фильтрация вместе с доработкой ревьюеров [10], то есть нужны и специализированные ревьюеры, и проверка. Мультиагентное ревью с проверяющим агентом – направление 2024–2026 годов [16, 27, 28, 42]. Но проверка каждого замечания по коду и по тексту правила самой команды, работа со своей моделью в self-hosted GitLab и оценка относительно живых ревьюеров вместе не заявлены ни у одного аналога (раздел 3).

У автора есть рабочий прототип такого конвейера, который применяется на ревью MR в коммерческом проекте: агенты по темам замечаний, проверяющий агент и пронумерованные соглашения команды. Количественной оценки прототипа пока нет. Он служит пилотной средой для эталона и замеров (задачи 2 и 5), а в работе дорабатывается до системы для self-hosted GitLab со своей моделью (задача 4).

Поэтому разработка и измеримая оценка мультиагентной системы, которая проверяет каждое замечание до публикации, своевременны.

### 4.2 Цель исследования

Снизить долю ложных замечаний автоматизированного ревью MR без существенной потери полноты за счет мультиагентной системы на основе LLM, в которой агенты по темам находят нарушения пронумерованных соглашений команды, а проверяющий агент сверяет каждое замечание с кодом и текстом правила до публикации. Ограничение: система работает в контуре компании с self-hosted GitLab, все вызовы идут к модели, развернутой в этом контуре.

Эталон и разметка. Эталон – замечания живых ревьюеров по правилам соглашений на реальных MR. Ложность замечаний системы определяют не менее двух разработчиков проекта, согласие разметчиков меряется коэффициентом каппа Коэна. Базовые линии: та же система без проверяющего агента, одноагентное ревью с теми же правилами и PR-Agent с той же моделью.

Целевые показатели:
- доля ложных замечаний снижается не менее чем в 1,5 раза по сравнению с той же системой без проверяющего агента;
- полнота относительно замечаний живых ревьюеров по правилам соглашений снижается не более чем на 15 % от полноты системы без проверяющего агента;
- не менее 80 % замечаний по соглашениям указывают правило, которое действительно нарушено в этом месте кода, по разметке выборки не менее 100 замечаний.

Обоснование показателей. В AutoCommenter отключение 17 неприменимых практик подняло долю полезных замечаний с 54 до 66 %, то есть доля бесполезных снизилась с 46 до 34 %, в 1,35 раза, причем грубым способом – отключением целых практик [14]. Проверка каждой находки в Semgrep отсеивает в среднем 60 % находок при 96 % согласия людей [49]. Поэтому для проверки каждого замечания принят ориентир «в 1,5 раза». LLM-фильтр предупреждений SharpChecker сохранял 80–97 % истинных предупреждений [9], отсюда допустимая потеря полноты 15 %. Порог 80 % верно указанных правил взят по целевому уровню полезности замечаний AutoCommenter для широкого внедрения [14]. Все три значения – рабочие гипотезы: базовые доли ложных замечаний и полноту для системы без проверяющего агента и для PR-Agent измеряют на эталоне (задача 5), после чего показатели уточняются.

### 4.3 Задачи исследования

1. Формализовать представление соглашений команды (номер, текст, область действия, примеры) и классификацию замечаний по темам: архитектура, код и именование, тесты, комментарии. Классификация опирается на типы замечаний из эмпирических исследований ревью [1, 3] и уточняется на эталоне.
2. Собрать эталон: замечания живых ревьюеров по правилам соглашений на реальных MR с разметкой тем и правил, очистить его от расплывчатых и неприменимых замечаний [6, 11]. Из истории ревью отобрать примеры принятых и отклоненных замечаний для настройки агентов.
3. Разработать архитектуру мультиагентной системы: агенты-искатели по темам и проверяющий агент, который получает доступ к коду репозитория и требует доказательство с указанием файла и строки [43]; учесть смещения LLM в роли судьи и риск ложного консенсуса [28, 29].
4. Доработать прототип до системы для self-hosted GitLab со своей моделью: получение изменений MR, запуск агентов, публикация прошедших проверку замечаний на русском языке.
5. Разработать методику оценки по доле ложных замечаний, полноте и доле верно указанных правил относительно эталона; сравнить систему с базовыми линиями из подраздела 4.2.
